# Remove retired Requests columns

Status: prepared and tested locally. No live script deployment, column deletion,
Make edits, or live submissions have been performed.

`Code.gs` is a complete replacement based on the user-supplied Apps Script.
It supports the existing 15-column Requests layout and the new 11-column layout.
It keeps the same Requests tab, endpoint payload and Events/Sessions schemas.
The migration uses a script lock shared with request writes, makes a full backup
of Requests, then deletes Deal Size, Current Gaps, Readiness and Fit Outcome.
Unexpected headers stop the operation rather than overwriting them.

## Cutover order

1. Pause the Make scenario and record its current Watch New Rows cursor/last
   processed row. Keep the cursor; the migration does not remove or reorder rows.
2. Open the bound Apps Script editor from the Requests spreadsheet. Preserve a
   copy/version of the existing code, replace it with `Code.gs`, and save.
3. Update the **existing** web-app deployment to a new version through Deploy →
   Manage deployments → select the current deployment → Edit → select a new
   version → Deploy. Keep the existing execution/access settings and URL.
   Saving editor code alone does not update a versioned web-app deployment.
4. Confirm that deployment uses this code and any pre-update executions have
   finished before running `migrateRequestsColumns`
   from the editor. Authorise the required bound-spreadsheet access if requested.
   It copies Requests to a timestamped backup tab and removes old N, J/K and H.
   A second run returns `already_migrated` and makes no further deletions.
5. Check the resulting A:K headers below and that the request rows/notes survived.
   Keep the backup. Do not delete columns manually or rename the original tab.
6. In Make, reselect/refresh the Requests sheet and its header/range configuration
   so the new fields are available. Remove the entire strong/medium fit filter.
   Map the notification using the table below. Allow an empty profile URL when
   company name exists, and include company name and notes in the notification.
   Watch only the original Requests tab, not the backup, Events or Sessions.
7. Confirm the field mappings and retain the existing row cursor before resuming
   Make. Do not choose all historical rows or reset its starting point.
   Requests accumulated during the pause should be processed once with the new map.

No live test is authorised by this document. A later explicitly agreed end-to-end
check should cover both a profile request and a business-name-only request.

## New Requests / Make mapping

| Column | Header | Request key |
| --- | --- | --- |
| A | Timestamp | generated by Apps Script |
| B | Name | name |
| C | Email | email |
| D | LinkedIn URL | linkedin_url (may be blank) |
| E | Company Name | company_name |
| F | Role | role |
| G | Offer / Business Summary | offer_summary |
| H | Commercial Focus | commercial_focus |
| I | LinkedIn Current State | linkedin_current_state |
| J | Specific Notes | specific_notes |
| K | Source | source |

The website can continue sending retired keys: they are ignored after migration.
No website endpoint change is needed. Events/Sessions still retain their own
Fit Outcome columns for compatibility; only Requests is migrated.

If the migration reports a failure, keep Make paused and inspect the backup and
current headers before making further changes. A partial/unknown layout causes
new request writes to return an error rather than write misaligned data. Do not
roll back to the old Apps Script against the reduced sheet: it restores the old
headers. Retain the dual-layout code while resolving Make mapping problems.

Run offline checks with `node apps-script/test.cjs` from the repository root.

Deployment reference: https://developers.google.com/apps-script/concepts/deployments
